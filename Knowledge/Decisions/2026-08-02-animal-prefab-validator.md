# Тулза генерации префабов животных (валидатор + генератор)

**Дата:** 2026-08-02
**Статус:** обе фазы реализованы; генератор сверен с эталоном

## Контекст

Ручная сборка `Pteranodon.prefab` заняла ~49 минут и уехала с критическим багом (`UnitSize {2,1}`).
Решено сделать тулзу генерации префабов, но **сначала валидатор** — он окупается немедленно и
становится доверенной основой для генератора. См. план `/loop`-сессии и [[2026-08-01-pteranodon-enemy-prefab]].

## Принятое решение

Разделение союзников и врагов живёт **в системе типов**, а не во флаге: `AnimalSideProfile` с двумя
`static readonly` инстансами, у каждого свой слой, `Direction`, маска атаки, цвет радиуса хода, папка
вывода, имя коллайдер-ребёнка и базовый тип фасада. Сторона выводится **из папки ассета**, а не из
фасада — иначе правило «фасад соответствует стороне» не могло бы сработать в принципе.

`AnimalFootprint` — enum `{Small1x1, Medium1x2, Large2x2}` вместо `UnitSize`. Ловушка `{2,1}` перестаёт
быть правилом и становится непредставимой на уровне типа.

Аниматор-контроллеры **никогда не чинятся автоматически**: смена типа `IsDead` с Trigger на Bool
инвалидирует все условия переходов, ссылающиеся на него. Только репорт.

## Результат аудита 12 префабов — 19 ошибок, 34 предупреждения

**`Pteranodon` — единственный префаб без единой находки.** Он собирался вручную ровно по этим
правилам, так что это подтверждение, что набор правил кодирует именно тот опыт.

| Правило | Находки |
|---|---|
| **R8** `IsDead` объявлен Trigger, а `AnimalAnimator` зовёт `SetBool` | **5**: Cheetah, Fox, Hedgehog (`AC_Porcupine`), EnemyCheetah_Temp, Velociraptor. Смерть не проигрывается вообще |
| **R11** нет перехода Any State → Death по `IsDead` | **8**: все, кроме Pteranodon и Deer. Смерть не проигрывается при гибели в движении или атаке |

| R21 `applyRootMotion` включён | 1: Deer |

## Три правила пришлось смягчить после первого прогона

Первый прогон дал 27 ошибок и 33 предупреждения, из них значимая часть — ложные:

1. **R7 `cullingMode`** ловил `CullUpdateTransforms` на 9 префабах. Неверно: при этом режиме
   стейт-машина продолжает работать и события срабатывают. Опасен только `CullCompletely`.
2. **R4 второй `Animator`** был Error на 8 префабах, и все — из-за косметического пропа
   `Fox tail Variant` с собственным контроллером без параметров. Понижено до Warning: настоящая
   ловушка (компонент атаки не на том объекте) покрыта отдельным правилом R3.
3. **R22** искал merge-ребёнка **по имени** `Merge` и выдавал ложный варнинг на ежа, у которого
   он называется `Collider`. Исправлено на поиск по компоненту `MergeTarget`.

> **Урок:** правило, дающее ложные срабатывания пачками, обесценивает весь инструмент — на него
> перестают смотреть. Первый прогон валидатора надо разбирать находку за находкой и смягчать,
> а не праздновать количество.

## Технические заметки

- `GridManager.GetFootprint` — `private static`, читается рефлексией с корректным пропуском правила,
  если метод исчезнет.
- Приватные сериализованные поля читаются через `SerializedFieldReader` с проверкой
  `SerializedPropertyType` — та же защита, что закрывает ловушку «`floatValue` на int-поле молча
  пишет 0».
- Варнинги через `Debug.LogWarning` **не дошли до консоли** при чтении через MCP (в консоли Unity,
  похоже, выключен фильтр Warning). Для проверки результатов надёжнее вызывать валидатор напрямую
  через `execute_code` и собирать находки в строку, а не читать консоль.

## Фаза 2 — генератор

Пункты меню: `Build Ally Prefab From Recipe`, `Build Enemy Prefab From Recipe`,
`Build All Animal Recipes`, `Add Attack Animation Event`. Первые два читают
`Selection.GetFiltered<AllyAnimalRecipe>` / `<EnemyAnimalRecipe>` и внятно ругаются на чужой тип —
разделение сторон видно в UI без единой строки UI-кода.

Конвейер: префлайт (`RecipePreflight`, ничего не пишет на диск) → гейт перезаписи → сборка в памяти
→ `SaveAsPrefabAsset` + `ImportAsset` → **перечитывание с диска и прогон полного валидатора**.

### Формула вывода геометрии — переделана относительно плана

План предлагал `радиус = Max(extents.x, extents.z)`. **Проверка по трём эталонам это опровергла:**

| | Pteranodon | Velociraptor | T-Rex |
|---|---|---|---|
| `Max(extents.x, extents.z)` | 2.95 | 2.26 | 6.27 |
| авторское значение | 1.2 | 0.92 | 3.35 |

Баунды раздуты крыльями (X у птеранодона 5.91 — размах) и хвостами (глубина меша T-Rex 12.55 при
футпринте 2×2). Итоговые формулы:

- **радиус** = `min(полудиагональ футпринта / planarScale, max(extents.x, extents.z))`.
  Для 1×1 при scale 0.8 даёт 0.88 — против авторских 0.92 у велоцираптора почти точное попадание.
- **центр коллайдера** = `(0, bounds.center.y, 0)`. Вертикаль по баундам ложится хорошо
  (птеранодон точно, велоцираптор −5 %, T-Rex +14 %); горизонталь по баундам непригодна — авторские
  центры сдвинуты вперёд от центра меша, потому что хвост тянет баунды назад.
- **AttackPoint** = `(0, bounds.center.y, радиус)`. У птеранодона совпало точно (1.2 при радиусе 1.2).
- **высота хелсбара** = `bounds.max.y * rootScale.y`. Ложится на птеранодона и велоцираптора,
  но не на T-Rex (5.5 против авторских 2.8) — крупным моделям бар ставят заметно ниже верха.

> **Урок:** «сверено с эталоном» в плане не значит сверено. Формулу написал планировщик, я утвердил
> план не перепроверив, и она разошлась с реальностью в 2.5 раза. Спас пункт проверки
> «сгенерировать эталон заново и сдиффать» — его стоит держать в любом плане, где есть формула.

### Приёмка: птеранодон, собранный заново

**22 из 25 сериализованных полей совпали с ручной сборкой, валидатор на сгенерированном префабе даёт
0 находок** — столько же, сколько на ручном. Расходятся только три выводимых числа
(радиус 0.88 против 1.2, AttackPoint z 0.88 против 1.2, хелсбар 0.99 против 1.3) — там, где ручные
значения подбирались на глаз. Принципиально правильны, скорее, выводимые: 0.88 × 0.8 = 0.707 мировых
единиц — ровно полудиагональ клетки 1×1.

Рецепт `Assets/Settings/Animals/Recipes/PteranodonRecipe.asset` оставлен как рабочий пример, с тремя
включёнными переопределениями под текущие ручные значения — пересборка воспроизведёт префаб как есть.

### Две правки после дифа

1. **Цвет радиуса хода врага** был `alpha 0.35` (дефолт из кода `AnimalMovement`), у эталонов `alpha 1`.
2. **`isTrigger` коллайдера сделан зависимым от стороны**, вопреки плану. План предлагал
   стандартизовать на `true` везде; но все три реальных врага используют `false`, а дрейф
   (`Chicken` с `isTrigger: 0`) есть только среди союзников. Итог: союзник `true`, враг `false` —
   дрейф лечится там, где он есть, и не создаётся там, где его не было.

### Вычистка вендорских компонентов

Модели polyperfect несут на корне `Dino_WanderScript`, `CharacterController`, `NavMeshAgent`, которые
дерутся с `AnimalMovement` за трансформ. Ассемблер сносит с корня **все `MonoBehaviour`, чей неймспейс
не начинается с `Code.`**, плюс `NavMeshAgent` / `CharacterController` / `Rigidbody`. Правило
универсальное — не список известных вендорских классов, который бы протух.

### Что генератор делать отказывается

Фасад союзника (обязан сконструировать `MergeSkill` — это проектирование, а не бойлерплейт),
правка `GridManager.GetFootprint` (только валидация с печатью нужной строки), любые мутации
аниматор-контроллеров, перезапись стат-ассета с другим классом.
